# Adaptive Floor Heating Climate

Home Assistant용 학습형 바닥난방 Climate 커스텀 통합입니다. 단독 모드의 HEAT/AUTO 운전, 재실·외출 프리셋, 기본 히스테리시스 제어, 열 반응 관측과 학습 기반 예측 ON/OFF를 구현했습니다. 각방 난방 런타임은 후속 단계입니다.

## 개발 상태

- 현재 작업 브랜치: `dev`
- 통합 도메인: `adaptive_floor_heating`
- 설치 경로: `custom_components/adaptive_floor_heating/`
- 설정 방식: Config Flow에서 단독 제어 또는 각방 제어 선택
- 단독: 히터 스위치 1개 + 실내 온도 센서 1개
- 각방: 방 수(1~32)를 입력한 뒤 방마다 스위치와 온도 센서를 한 쌍씩 선택
- 같은 스위치의 방 간·통합 간 중복 등록 방지(진행 중인 설정 포함)

## 설정 흐름

Home Assistant에서 통합 추가 → Adaptive Floor Heating Climate → 제어 방식을 선택합니다. 각방 설정은 `1번 방 / 전체 N개 방` 순서로 진행하며 마지막 방까지 입력한 뒤 한 번에 저장합니다. 취소한 설정은 저장하지 않습니다. 설정 도중 이전 방의 엔티티가 사용할 수 없는 상태가 되면 다시 설정하도록 안내합니다.

Config Flow 자체는 장치를 켜거나 끄지 않습니다. 단독 설정을 저장하면 Climate와 진단 센서가 생성됩니다. 기본 운전 모드는 OFF입니다. 각방 설정에는 공용 보일러를 추가로 요구하지 않으며, 현재는 해당 모드에서 장치를 제어하지 않습니다.

## 단독 모드 사용

기존 단독 설정을 삭제할 필요 없이 통합 파일을 갱신하고 Home Assistant를 재시작하면 Climate가 생성됩니다. 설정 → 기기 및 서비스 → 해당 통합의 엔티티에서 확인할 수 있습니다.

단독 온도조절기는 서비스형 기기로 등록되며, Climate는 해당 기기의 주 엔티티로 연결됩니다. 설정 → 기기 및 서비스 → 기기에서도 확인할 수 있습니다. 기존 Climate의 고유 식별자는 유지합니다. 연결한 히터와 온도 센서는 원래 통합 소속을 유지합니다. 기기 등록은 [공식 Device Registry 문서](https://developers.home-assistant.io/docs/device_registry_index/)의 `DeviceInfo` 방식을 따릅니다.

- Climate 운전 모드는 OFF, HEAT, AUTO입니다. HEAT는 기본 히스테리시스 제어, AUTO는 학습 기반 예측 제어를 사용합니다. OFF에서는 자동 제어를 하지 않고 외부 히터 동작을 관측·학습합니다.
- HOME/AWAY 프리셋은 각각 기본 23°C/18°C이며, 통합 옵션에서 18~30°C 범위로 조정할 수 있습니다. 프리셋을 선택하면 그 온도가 목표온도에 적용됩니다. 옵션에서 프리셋 온도를 바꾸면 해당 기본값을 사용 중인 목표온도도 재로드 후 갱신하며, Climate에서 직접 조정한 목표온도는 유지합니다.
- 기본적으로 목표보다 0.2°C 낮아지면 ON, 0.2°C 높아지면 OFF를 요청합니다.
- 최소 ON은 15분, 최소 OFF는 10분입니다. 사용자 OFF, 센서 오류와 과열 정지는 최소 ON보다 우선합니다.
- 재시작 후에는 새 온도 보고와 확인된 OFF가 필요합니다. OFF 확인부터 최소 OFF 시간을 기다리므로 HEAT를 선택해도 바로 켜지지 않을 수 있습니다. 새 보고 전에는 Climate가 unavailable로 표시됩니다.
- 통합의 구성/옵션에서 온도 편차, 최소 ON/OFF 시간, 센서 보고 대기 한도(기본 15분)를 변경할 수 있습니다. 저장 시 안전 정지 후 재로드합니다.
- 현재 목표온도, 요청 모드, 선택 프리셋과 오류 잠금을 저장합니다. 재시작 후 활성 모드를 복원해도 위 시작 조건을 다시 적용합니다. 이전 `자동 제어` 스위치 ON과 HEAT 조합은 AUTO로 이전합니다.

센서가 unknown/unavailable이거나 유효한 온도를 보고하지 않으면 난방을 정지합니다. 센서 복구는 30초 이상 간격의 정상 보고 두 번으로 확인합니다. 35°C 이상 과열, 히터 통신·명령 오류 또는 외부 스위치 조작은 오류 잠금을 유지하며, 원인 해소·OFF 확인·최소 OFF 시간 이후 HEAT를 명시적으로 선택해 재개합니다. 과열 잠금은 34°C 이하에서 해제할 수 있습니다.

기기에는 진단 범주의 열 관측·학습 센서가 추가됩니다. 지연 시간은 duration, 잔열 상승은 temperature delta device class를 사용하고, 누적 사이클·제외 건수는 total-increasing 통계로 기록합니다. 각 센서에는 지표 의미에 맞는 아이콘이 설정됩니다. 변화율·가열률·신뢰도는 의미에 맞는 표준 device class가 없어 지정하지 않습니다. 온도 기울기는 최대 24시간/4,096개 보고를 보관하고 최근 45분 구간으로 회귀 계산합니다. 난방 반응·잔열 값은 확인된 스위치 전환과 완결된 관측만 사용합니다. Phase 2 관측은 제어 결정과 히터 명령에 영향을 주지 않으며, 재시작 시 진행 중인 이력·사이클을 버립니다.

완결된 관측 사이클은 난방 반응 지연, 가열률, 잔열 상승, 최고점 지연을 각각 EWMA(alpha 0.2)로 학습합니다. 3개 기준 표본 이후에는 표준편차 3배 또는 항목별 최소 편차를 넘는 이상치를 제외합니다. 기기에서 학습 추정값, 신뢰도, 반영·제외된 사이클 수와 제외 측정 수를 확인할 수 있습니다. 집계 모델은 런타임 설정과 별도 저장소에 영구 저장합니다. AUTO에서는 유효한 냉각 기울기와 신뢰도 보정된 학습 반응 지연으로 온도가 반응 시점에 목표 이하가 될 것으로 예상되면 미리 가동합니다. 잔열 기반 정지는 학습 신뢰도를 반영하고 최소 ON 시간을 지킵니다. 히터가 꺼진 동안에는 잔열 추정값으로 재가동 시점을 조정합니다. 학습값 또는 유효한 기울기가 없으면 기본 히스테리시스와 타이머를 사용합니다.

Climate 속성의 `control_state`, `faults`, `heater_confirmed_on`, `heater_command_pending`으로 대기·오류·명령 확인 상태를 확인할 수 있습니다. `hvac_action`은 확인된 스위치 상태를 나타내는 대리 지표로, 실제 버너 점화나 열공급 측정값은 아닙니다. HA의 센서 보고 시각과 낙관적 스위치 상태는 물리적 장치의 측정·동작을 보장하지 않습니다.

정상 재로드·제거에서는 OFF 확인 실패 시 감시를 유지하고 해제를 실패 처리합니다. HA 강제 종료·정전·통신 단절에서는 소프트웨어 OFF를 보장할 수 없습니다.

## 로컬 설치 경로

개발 중인 통합 폴더를 Home Assistant 설정 디렉터리의 `custom_components/adaptive_floor_heating/`에 복사하거나 링크한 뒤 Home Assistant를 재시작합니다. 기존 단독 Config Flow는 사용자 환경에서 동작을 확인했습니다. 이번 Climate·난방 런타임의 실제 HA 검증과 HACS 배포 메타데이터 보완은 남아 있습니다.

## Windows 개발 검증

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-test.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests/components/adaptive_floor_heating -p "test_*.py" -v
```

Windows Python 3.14.5에서 73개 테스트를 통과했습니다. 순수 열 관측·학습·제어 로직, 실제 voluptuous, HA 인터페이스 대역과 시험용 스위치를 사용해 설정·시간 경계·명령 확인·실패 복구·저장·재로드를 검사합니다. HA 런타임과 프런트엔드의 통합 검증을 대체하지 않습니다. 구현 시 참조한 API 기준은 Home Assistant 2026.9.3이며 지원 최소 버전은 실제 HA 검증 후 확정합니다.

## HACS 배포 준비

퍼블릭 HACS 배포 전에 코드 소유자와 브랜드 아이콘을 확정하고 `manifest.json` 및 HACS 검증 요구사항을 보완해야 합니다.
